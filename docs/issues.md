## 问题 1：服务器容器重建时 AUTH 变量被意外覆盖导致凭据失效

### 现象

服务器 Stack 容器重建后，统一 Agent（`triage-operator`）对 OctoBus 网关的
鉴权统一失败：能力调用在取数阶段即返回鉴权错误，工作流 fail closed 中断，
本地无法通过任何 `OCTOBUS_*` 配置复现（本地凭据一直有效）。

### 定位过程

1. 对比部署前后 `daemon` 侧 `.env` 与 compose 文件中的变量映射，
   发现重建后的 `.env` 中 `AUTH_*` 相关变量的取值与受控备份不一致；
2. 回溯部署操作记录，确认根因是本地 PowerShell 批量替换脚本在修改变量名时
   未限定作用范围，误伤了 `AUTH_*` 变量的取值（被替换成同批次的通用占位值）；
3. 用受控备份中的旧值逐一比对受影响变量，确认仅 `AUTH_*` 家族受损，
   其余 `OCTOBUS_*` / `LLM_*` 变量未被波及。

### 解决方式

- 从 daemon 侧的受控备份（root-only `.env` 备份）恢复 `AUTH_*` 凭据原值；
- 修正批量替换脚本的作用范围：显式声明允许改动的变量清单，
  清单之外的变量一律不触碰；
- 恢复后重跑 `deploy-and-verify.sh` 的 `verify`（全量验证）确认鉴权链路恢复。

### 改进方向

- 敏感变量改名走**显式清单**（allowlist），禁止对 `.env` 做无范围的批量替换；
- 替换脚本执行前先输出**预检 diff**（只显示变量名与变更类型，不回显取值），
  人工确认后再落盘；
- 事后轮换 `AUTH_SECRET`：既然取值曾被覆盖写盘，按规范按泄露处理，
  完成一轮密钥轮换并更新受控备份。

## 问题 2：统一 CLI 域前缀环境变量别名不生效

### 现象

在统一入口（`agent/src/interfaces/cli.js`）配置
`SECURITY_TRIAGE_OCTOBUS_BASE_URL` 等域前缀变量后，变量未按预期回退到统一
`OCTOBUS_*` 变量，CLI 仍报 `Missing required value: OCTOBUS_BASE_URL`；
直接设置无前缀的 `OCTOBUS_BASE_URL` 则正常。

### 定位过程

1. 复现：只设域前缀变量运行 `--workflow security`，稳定报缺配置；
   只设统一变量则成功——问题锁定在别名解析环节；
2. 阅读 `agent/src/config/env.js` 的 `aliasDomainEnvironment` 与
   `cli.js` 的调用顺序，发现别名回退的**优先级判断有误**：
   在特定解析顺序下，域前缀变量被通用名是否已设置的判断提前短路，
   导致本应生效的回退赋值没有执行；
3. 用最小环境变量组合（前缀变量 / 通用变量 / 两者都设 / 都不设）
   构造矩阵用例，确认只有"仅设置前缀变量"这一格失败。

### 解决方式

- 修正 `agent/src/config/env.js` 中前缀回退的优先级逻辑：
  通用名未设置且域前缀变量存在时才回退，两变量并存时以通用名为准；
- 为别名矩阵补单元测试（前缀 / 通用 / 并存 / 缺失四格全部覆盖），
  防止回归。

### 改进方向

- 别名映射改为**矩阵表驱动测试**：每个域前缀（`SECURITY_TRIAGE_` /
  `MALWARE_TRIAGE_`）× 每个变量对 × 四种设置组合，一次生成全部用例；
- 新增变量对时同步登记到矩阵表，缺一行即测试失败。

## 问题 3：部署脚本 docker compose 子命令拼接顺序错误导致部署中断

### 现象

执行 `deploy-and-verify.sh` 部署时，deploy 阶段容器未按预期拉起，
脚本中途退出，Stack 内旧容器仍在运行、新配置未生效。

### 定位过程

1. 重放部署日志，发现 docker compose 实际收到的命令与脚本意图不符：
   子命令与参数的拼接顺序错误，且引号包裹把多个参数并成了一个；
2. 逐段检查 shell 脚本中命令拼接处的引号与数组展开写法，
   定位到拼接处把子命令位置当成了参数位置；
3. 在本地用 `set -x` 干跑（不实际执行 docker）验证修复后的拼接结果。

### 解决方式

- 修正脚本中 docker compose 子命令的拼接顺序与引号写法；
- 在部署前增加 `fast-verify` 预检步骤：先以只读命令核对 compose 配置
  与变量映射，预检通过才进入实际部署。

### 改进方向

- 部署脚本纳入 **shellcheck** 检查（CI / 提交前本地各跑一次），
  引号与拼接类问题在静态阶段即暴露；
- 脚本内所有含变量的命令统一使用数组展开（`"$@"` 风格）传参，
  避免字符串拼接引号歧义。

## 问题 4：CLI 级审计测试中 spawnSync 阻塞事件循环导致子进程 fetch 超时

### 现象

CLI 级审计测试（以子进程方式拉起真实 CLI、本地 HTTP 网关替身承接请求）中，
本地网关替身对子进程的请求无响应；子进程内 fetch 三次重试全部超时，
CLI 以退出码 2 退出，测试间歇性失败。

### 定位过程

分层对照实验逐步缩小范围：

1. **进程内 fetch**：在同一进程内直接 fetch 网关替身端口——正常返回，
   网关实现本身无问题；
2. **跨进程原始 TCP**：用原始 TCP 客户端跨进程连接网关端口——可完成
   TCP 握手，说明端口监听与网络栈正常；
3. **跨进程 fetch**：以子进程方式发起 fetch——挂起无响应。

三层对照锁定差异只在"跨进程 + fetch"组合。进一步分析：网关替身与测试运行在
**同一 Node 进程**，而测试用 `spawnSync` 同步等待子进程退出——同步等待期间
父进程事件循环被完全阻塞，网关替身的 HTTP 服务无法响应任何请求；
子进程侧表现为 fetch 挂起 → 重试 → 超时。

### 解决方式

- 测试改用**异步 `spawn`** 驱动子进程（`await` 子进程退出，不阻塞事件循环），
  网关替身得以正常服务；
- 为子进程增加 **30 秒看门狗**超时：超时即杀死子进程并判定测试失败，
  防止挂起用例拖垮整个测试批次。

### 改进方向

- 跨进程测试**一律异步**驱动子进程，禁止在持有事件循环依赖（本地 HTTP
  替身 / 定时器 / 流）的进程内使用同步 spawn；
- 所有子进程测试显式声明超时（看门狗），超时信息中带上子进程 PID 与
  已收到的输出片段，便于定位挂起点。
